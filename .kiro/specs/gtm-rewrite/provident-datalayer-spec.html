Architecture Overview

Production-grade dataLayer architecture for the provident.pl platform, built on Next.js (React) and Sanity CMS.

The dataLayer is the single source of truth between the frontend application and all marketing and analytics systems — including analytics platforms, advertising platforms, customer engagement tools (e.g. MoEngage), experience analytics (e.g. ContentSquare), and CRM / CDP / BI systems. All communication flows through Tag Manager and server-side tagging, keeping the frontend completely vendor-agnostic.

What this document covers

  • Long-form loan application (Provi Direct)
  • Short forms and their thank-you pages
  • Product and landing pages
  • Login and authenticated area
  • Calculator interactions
  • Global user identifiers and session context
  • Detailed field- and step-level error tracking for the loan funnel

Dual-Layer Event Model

Every interaction on the site maps to one of two event layers. Using the correct layer for each interaction is mandatory.

Strategic Events
Business-level events used for analytics, attribution, marketing and BI. These represent meaningful moments in the user journey.
page_view · checkout · purchase · form_page_view · generate_lead · calculator_update · login · logout · ui_interaction · dashboard_view · dashboard_action · consent_update
gaevent
Operational micro-interaction event for form fields, errors, step validation, and calculator UI. Tracks the granular detail of how users interact with forms.
Preserves historical continuity in GA4, GTM and downstream systems. All new form tracking must use this event name.
All new implementations must respect this dual-layer model. Use strategic events for core business actions and page/step views. Use gaevent for granular UI/UX interactions and error tracking.

Global Context Variables

These fields carry user identity and session state. They must be included on every strategic event, wherever the data is available.

Think of global context as the "who and where" layer. It lets the analytics system answer questions like: "Was this a logged-in user? A new or returning customer? Which marketing campaign brought them here?" — across every event type.

Required Fields

FieldTypeDescriptionExample
user_logged_in boolean Whether the user is currently authenticated. false
login_method string Method used to log in. Use "unknown" when not logged in. "email" / "pesel" / "unknown"
user_status string Customer type: "NC" = new customer, "RS" = returning customer. "RS"
email_sha string SHA-256 hash of the normalized email address. Send the string "undefined" if not available — never omit the field. "b1d5b9bd..."
tel_sha string SHA-256 hash of the normalized 9-digit phone number. Send "undefined" if not available. "bab0ffc..."
ss_custom_session_id string Server-generated session identifier. Provided by the backend — the frontend just forwards it. "1703445343"
ss_custom_client_id string Server-generated device/client identifier. Provided by the backend — the frontend just forwards it. "A43d-b834-gLkJ4Y78-1703445343"
prov_mkt_id string Marketing campaign identifier. Read from the URL or provided by the backend. "x36cy7k92j"
entry_location string Where the user entered the loan funnel from. "Main Page" / "Landing Page" / "Product Page" / "Other"

Hashing Rules

All PII must be hashed before being pushed to the dataLayer. The process must happen in the frontend (client-side) or in a controlled backend endpoint — never by passing raw data through GTM.

Email → email_sha

  • Lowercase the entire email address (e.g. [email protected] → [email protected])
  • Trim all leading and trailing whitespace
  • Apply SHA-256 hashing to the result
  • If the email is not yet available, push the literal string "undefined" (not JavaScript undefined)

Phone → tel_sha

  • Remove the country code +48 if present
  • Remove all spaces and non-numeric characters
  • Keep the resulting 9-digit local number
  • Apply SHA-256 hashing
  • If unavailable, push the literal string "undefined"
Privacy rule: Raw email addresses and phone numbers must never appear in the dataLayer or be sent to any marketing vendor. Only SHA-256 hashed values are permitted. This is a GDPR requirement.

Loan Data Model

The Provi Direct long-form application uses a structured data model that must be included in every application event (checkout and purchase). This section defines all the building blocks.

Each application event contains six groups of data:

  • Loan product definition (ecommerce.items)
  • Application state (step name, IDs)
  • User identity (hashed email, phone, customer type)
  • Session / device identifiers
  • Loan amount and term model
  • Marketing and entry context

Items Array — The Loan Product

The loan product is represented as a single item inside ecommerce.items. The array always contains exactly one element because a single application concerns one product. Quantity is always 1.

Loan Amount Model

The loan amount evolves through the application process. Four distinct amount fields track this journey. Not all are available on every step — follow the propagation rules below.

ParameterTypeDescriptionExample
initial_loan_amountnumberThe amount the user selected at the very start of their application.8000
proposed_loan_amountnumberThe first amount proposed by the system after internal risk evaluation.6000
final_loan_amountnumberThe final offer amount shown to the user before acceptance.5000
accepted_loan_amountnumberThe amount the user actually accepted and submitted.5000

Loan Amount Propagation Rules

Which amount fields are required depends on how far through the process the user is. Earlier steps don't have all four values yet.

Step in the applicationRequired amount fields
Early steps — contact, identity, addressinitial_loan_amount only. Others may be undefined.
Offer generation — digital-offer stepinitial_loan_amount + proposed_loan_amount
Final offer stepfinal_loan_amount MUST appear
Checklist-consent stepaccepted_loan_amount MUST appear
purchase (final confirmation)All four fields are required: initial_loan_amount, proposed_loan_amount, final_loan_amount, accepted_loan_amount
ecommerce.value and items[0].price should always mirror the most contextually relevant amount for each step (initial → proposed → final → accepted), following the propagation rules above.

Selects, Checkboxes & Consents

Non-text fields (dropdowns, checkboxes, radio buttons, consent toggles) use the same field-level event model as text inputs. No special handling is needed — just include the value field.

The only difference from a text field event is that value is populated for these types (e.g. "YES" / "NO" for consents), whereas it is optional for text inputs.

page_view — SPA Virtual Page Views

In a Single Page Application (SPA), the browser does not reload between screens. This means GTM never sees a natural page load. The application must manually push a page_view event every time a new screen renders.

When to fire: On every new logical view: Home, product pages, content/info pages, error pages.

Exceptions: Loan application steps use checkout. Do not double-fire.

Short form pages: As of June 2026, pages with short forms fire a standard page_view with page_type: "form_page" (set via Sanity CMS). The separate form_page_view event is no longer used in the provionline-sanity-web implementation.

Server-Side Tagging Architecture

This section explains how the frontend dataLayer feeds into Server-Side Google Tag Manager (sGTM), and what each layer of the system is responsible for.

The architecture is privacy-first and vendor-agnostic. The frontend never speaks directly to any analytics or marketing vendor. All vendor communication, data transformation, and identity linking happens exclusively in sGTM — the central hub for the entire measurement ecosystem.

Why This Architecture?

Privacy by design
No vendor scripts run in the browser. No PII or vendor IDs are handled client-side. Only hashed identifiers cross the boundary.
ITP / ETP resilience
Server-generated ss_custom_session_id and ss_custom_client_id maintain attribution continuity in Safari, Firefox, and Chrome with 3PC deprecated.
Stable frontend contract
The dataLayer schema never needs to change when vendors add new requirements. All mapping happens server-side.
Centralised logic
Routing, identity linking, consent enforcement, and transformation happen once — in sGTM — not duplicated across systems.

Three-Layer Responsibilities

Layer 1 — React Frontend

  • Push structured events exactly as defined in this document
  • Include only normalized business parameters — never vendor-specific fields
  • Forward hashed identifiers (SHA-256 only)
  • Include server-generated session identifiers verbatim
  • Reset ecommerce before every ecommerce event
  • Debounce rapid interactions
  • Never implement GA4, Ads, Floodlight, or any other vendor logic

Layer 2 — GTM Web

  • Listens for dataLayer events
  • Extracts parameters and applies optional pre-validation
  • Forwards the complete payload to sGTM via HTTP
  • Attaches consent state
  • Contains no mapping or transformation logic

Layer 3 — Server-Side GTM (sGTM)

  • Receives normalized JSON payloads from GTM Web
  • Enriches with server timestamp, IP (if consented), User-Agent, geolocation
  • Applies business rules: privacy filtering, consent enforcement, validation
  • Maps and routes events to all configured destinations (GA4, Ads, CRM/CDP, BI)
  • All vendor-specific transformations happen here — nowhere else

Identity & Session Model

The same identity fields are used consistently across every event type — page views, calculator, short forms, long application, login, dashboard, and logout. This consistency allows sGTM to reconstruct complete customer journeys across:

  • Anonymous visitor → lead → login → application → dashboard
  • Cross-device behaviour (via server IDs)
  • Repeat visits and ITP-restricted contexts (Safari / iOS)

Privacy & Consent

LayerResponsibility
FrontendNo raw PII. Default Consent Mode set to denied before GTM loads. Runtime consent updates via CMP (OneTrust).
sGTMConsent-based filtering. Suppression of identifiers for non-consenting users. No unnecessary PII stored. Propagation rules enforced for downstream systems.

Versioning & Change Control

This document represents v1 of the canonical dataLayer schema.

Breaking changes (field renames, type changes, removals) require a new version (v2, v3...) with temporary dual-writing in sGTM and a communicated deprecation timeline.

Non-breaking changes (new optional parameters, new event types, new metadata fields) can be added without a version bump.

Core principle: The frontend dataLayer must remain as stable as possible. All complexity lives in sGTM.

Implementation Boundaries

Strict rules that govern what each layer of the system is and is not permitted to do. These boundaries are not guidelines — they are architectural requirements that must not be violated.

Vendor Mapping Rule (critical): All vendor mapping, data transformation, enrichment, identity linking, and request routing MUST be performed exclusively inside the Server-Side GTM container. The frontend MUST NOT implement vendor-specific logic of any kind.

Frontend Rules

Frontend MUST

  • Push events exactly as defined in this document
  • Include only normalized business parameters
  • Forward hashed identifiers (SHA-256)
  • Include server-generated session identifiers
  • Reset ecommerce before each ecommerce event
  • Respect debounce rules

Frontend MUST NOT

  • Implement GA4 mapping logic
  • Implement Ads / EC / Floodlight logic
  • Send requests directly to vendor APIs
  • Add vendor-specific parameters
  • Attempt identity linking or fingerprinting
  • Modify data for third-party purposes
  • Add fields not defined in this document

Server-Only Responsibilities

The following tasks belong exclusively to sGTM and must never be implemented in the frontend or GTM Web:

Processing

  • Event routing
  • Consent enforcement
  • Vendor mapping
  • Identity linking
  • Data normalization
  • Payload transformation

Security & Ops

  • Token handling
  • Request signing
  • Debugging and logging
  • De-duplication
  • Rate limiting
  • Traffic filtering
  • Error handling and retries
